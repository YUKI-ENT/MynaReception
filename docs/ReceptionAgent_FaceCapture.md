# face XML自動取込・iCall予約取得

## 設定と操作

1. Dynamicsの「患者マスター」を開き、iCallManagerを起動する。
2. ReceptionAgentの「設定」で次を指定する。
   - face XML出力フォルダー
   - DynamicsがXMLを移動するtrashフォルダー（実際の移動先を指定。直下のファイルを対象）
   - UTF-8またはShift_JIS（CP932）
   - iCallManagerのrequest（req）とresponse（res）の実フォルダー。UNCパスも利用可能。
   - 来院確認／連携を実行するか。初期値は両方OFF。ONの場合はiCallManager側も「実操作を有効化」が必要。
3. メイン画面で「監視開始」。設定変更は監視停止後に行う。
4. DGVで患者ID・内部カルテ番号・予約番号・取込結果を確認する。行のダブルクリックで詳細・照合候補・操作結果を表示。

自動開始はしません。監視開始後は出力先とtrashを約1秒間隔（列挙・読み取り時間を除く）で巡回します。ファイル名 `OQSsiquc01res_face_*_yyyyMMddHHmmss.xml` の日付が当日のファイルだけを取り込みます。当日分は開始前に既に存在するファイルも対象です。古いtrash内のXMLから現在の予約を操作しないための制限です。サブフォルダーは走査しません。

既存の「手動患者検索（テスト）」は単独の照合確認用です。この画面からはDB保存・予約API送信を行いません。古いXMLも確認できます。

## ファイル回収とSQLite

取得と患者検索／API処理は独立して動きます。API応答待ち中も回収を続けます。

- 元XMLは `FileShare.ReadWrite | FileShare.Delete` で共有読み取り。削除・移動・上書きはしません。
- 300ms間隔の2回の内容一致とXML解析を確認。書込み途中は再試行します。1回の試行で読めない場合も次の巡回で再確認します。
- 読み取り中に出力先から消えた場合、trashの同名ファイルを探します。trash単独の巡回でも回収します。
- 取込後は保存済みXMLで照合するため、元XMLが消えても処理を続けられます。
- ファイル名を大文字小文字を区別しない一意キーとして重複処理を防ぎます。同名で内容が違う場合は競合を表示し、新たな処理を止めます。既に実行した外部操作は取り消しません。

DBは `%LOCALAPPDATA%\ReceptionAgent\Reception\reception.sqlite3`。元XML、ファイル名、作成日時、ファイル名の生成日時、取得元・取得日時、患者氏名／カナ／生年月日、保険情報、照合候補と選択患者ID・カルテ番号、予約番号、処理状態、要求ID、応答結果を保存します。作成日時は回収先ファイルで取得できた値です。

SQLiteはWALと同期書込みを使用します。患者情報を含むローカルDBで、暗号化・自動削除は未実装です。バックアップはアプリ停止後にReceptionフォルダーごと取得してください。履歴表示は最新500件ですが、DBと重複管理はそれ以前も保持します。設定とBulk Consoleの既存履歴は別管理です。

## 予約APIと再開

患者IDを特定した後、iCallManagerと同じJSON契約で `find` 要求を出力します。ファイル名は `ra-<取込ID>-find.json`。患者IDは文字列です。要求は一時ファイルへ書き込んでからrenameします。

応答はrequestId・patientId・requestFingerprintを照合します。予約番号取得後、設定がONなら `arrived` → `link` の順に送ります。操作要求には、findで得た予約番号と患者名も含め、iCallManager側で操作対象を再確認します。

要求内容をSQLiteへ保存してからreqへ公開します。タイムアウト・再起動後も同じ要求ID／内容を再利用します。応答ファイルは削除しません。iCallManagerの要求ジャーナルと組み合わせて、同じ要求のボタン二重実行を防ぎます。新しく取り込むXMLにはその時点の設定、保存済みの処理には保存済みの送信先／操作設定を使います。

来院確認の `invoked` はボタン呼出しを送信した結果です。連携の `linked` はiCallのON（〆）表示を確認した結果、`already_linked` は既にONのため押さなかった結果です。旧版の連携 `invoked` も受け付けます。いずれもDynamics側の受付完了を保証する表示ではありません。

- COM接続不可、共有フォルダー切断、応答未到着：10秒後から同じ段階を再試行。
- 患者未特定、予約なし、APIの失敗、応答不一致：要確認として保存。以後の操作へ進みません。
- 日付をまたいだ未完了処理：自動送信を止め、要確認にします。送信済み要求があればiCallManager側の結果も確認してください。
- 要確認・競合には自動再投入ボタンを設けていません。DB／要求IDを消して再実行すると重複操作の原因になるため、結果確認のうえで対応します。

初診・予約なし時の登録、Dynamics受付テーブル追加、発券、Kioskセッションとの対応付けは今回の対象外です。次に到着したXMLを特定のKiosk患者として扱う処理はありません。

## 確認

自動テストは架空患者・一時フォルダーのみを使用。SQLite再読込、重複・内容競合、共有読み取り中の追記とtrash移動、独立した監視／処理ループ、iCallManager実契約とのfingerprint一致、要求ファイル／応答の往復、タイムアウトと再開、操作ON/OFF、患者未特定、予約なし、日付制限を検証しています。実環境のDynamicsによる移動タイミングとiCallのボタン操作は現地確認が必要です。
