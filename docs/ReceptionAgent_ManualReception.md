# ReceptionAgent 手動受付・照会番号単件登録

## 現在の操作

メイン画面はXML処理結果一覧を中心に表示します。工程の電光表示とBulk Consoleへの入口は廃止しました。Kioskセッションは今回未実装です。

1. 設定でface出力先、trash、iCallManagerのrequest/response、OQSのreq/resの親フォルダーを指定します。
2. 監視開始で当日分のface XMLを取り込みます。ReferenceNumberがあれば枝番なしカルテ番号として直接使用し、Dynamicsの患者検索を省略します。ReferenceNumberがない場合はDynamicsで患者を検索します。取得したカルテ番号でiCallManagerへfindを送ります。
3. 患者・予約が特定済みの当日行を選び、「来院確認」「連携」を個別に押します。来院確認後に連携を自動実行しません。
4. 設定の「Dynamicsでカルテ番号を取得した場合、照会番号を自動登録する」をONにすると、次回監視開始後に取り込むXMLでDynamicsから患者を一意に特定した後、バックグラウンドで単件登録します。初期値はOFFです。照会番号あり・候補複数・過去日のXML・設定変更前の取込履歴は自動登録対象外です。OQSのreq/resフォルダー設定が必要です。

照会番号がないXMLで患者を一意に特定できた行は、「照会番号登録／結果再確認」を押せます。予約なしでも患者特定済みなら登録できます。
5. 一覧の照会番号登録列で「未要求／応答待ち／成功／失敗／登録済み（XML）」を確認します。応答待ちの履歴は画面を開いている間、自動で再確認します。行のダブルクリックで要求／応答ファイル名、結果コードとメッセージを確認できます。

DGVの「カルテ番号」は枝番なし患者IDです。保険情報と枝番あり内部カルテ番号は非表示にし、行の詳細で確認できます。登録結果のセルにマウスを置くと結果コード・メッセージを確認できます。

来院確認・連携の既存自動設定は適用しません。旧版が保存した未送信の自動操作要求は要確認として停止します。既にiCallManagerへ送信された要求を取り消す機能はありません。

## 単件登録

- OQSsiimm01req_yyyyMMddNNNN.xml → 同じ連番のOQSsiimm01res。Bulkの受付番号取得と02reqは使用しません。
- 照会番号はDynamicsで取得した枝番なし患者ID。資格情報は保存した元face XMLを再解析して使用します。
- ReferenceNumberがあるXMLは登録不要。氏名カナ・生年月日の候補が複数なら自動確定しません。
- Shift_JIS、standalone=no、保険者番号は左スペース埋め。空の記号・枝番は省略し、枝番を00に補完しません。
- ローカルWorkへ完成XMLを保存し、送信意図を永続化してからreqへ一時ファイルを書き、flush・リネームします。
- FileSystemWatcherと300ms間隔のスキャンを併用し、共有読み取りで2回同じ内容を確認します。
- 初回画面の応答待ちは最大30秒。タイムアウト・再起動後も画面の定期確認で応答を取り込みます。同じボタンで明示的に再確認することもできます。送信済み要求の再送はしません。
- 受付処理と登録履歴は分離しています。登録失敗で予約検索・来院確認を止めません。自動登録は予約の有無やKioskセッションの有無に依存しません。
- 医療機関コード・任意識別子の一致を確認し、返却照会番号がある場合は患者IDとの一致を確認します。SegmentOfResult、ErrorCode、ProcessingResultStatusを検査し、不明・重複する結果は成功扱いにしません。
- 自動登録の送信前エラーは一覧に「失敗（自動登録）」として表示し、詳細はセルのツールチップに表示します。自動で同じ行の登録を繰り返しません。資格情報や設定を確認後、手動ボタンから再確認できます。正常終了・エラー確定後の同一行からの再送は行いません。次回来院の新しいXMLから再試行できます。
- 元のface XML、OQSのreq/res/trashは削除・移動しません。

保存先は %LOCALAPPDATA%/ReceptionAgent/SingleReferenceRegistration/ です。取込ID単位のJSONに患者ID、要求名、状態、結果コード・メッセージ・日時を保存し、Workに送信XMLを残します。実行端末／Windowsユーザーは1つに固定してください。

## 確認状況

2026-09-30、ユーザーの実機で照会番号登録要求に対する正常応答が返ったとの報告と、マスク済みの結果XMLを受領しました。応答はUTF-8、MessageHeaderにSegmentOfResult=1、MessageBodyにReferenceNumberRegistrationInfoとProcessingResultStatus=1を持つ構造です。正常応答ではErrorCode・ProcessingResultCode・ProcessingResultMessageのタグが省略されていました。現在の解析コードでこの構造を扱えるため、製品コードの変更は不要です。

患者・資格情報を架空値に置き換え、同じ構造のUTF-8応答をファイル待機・解析・履歴保存まで通す回帰テストを追加しました。医療機関・任意識別子・返却照会番号の照合は継続します。次回の顔認証でface XMLにReferenceNumberが返ることは、引き続き実機で確認してください。
