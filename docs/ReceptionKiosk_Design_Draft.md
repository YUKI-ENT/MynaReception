# ReceptionKiosk 初期設計案

2026-10-02。職員による同一PCでのテストを初期対象とし、将来Kiosk専用MiniPCへ移す。これは設計案であり、Kiosk・通信API・セッション管理はまだ未実装。

## 構成と責務

- `ReceptionKiosk` を独立したWinFormsプロジェクトとして同じソリューションに追加する。同一PCでは通常のウィンドウでテストし、専用端末運用では患者向け全画面表示に切り替える。
- ReceptionAgentを職員用の統括コンソールにする。XML監視、患者照合、予約照会、WKO確定番号検証、照会番号登録、Kioskセッション、設定、職員確認を管理する。
- ReceptionAgent.Coreへセッション・案内決定のロジックを置く。KioskとAgentで共有する通信モデルは小さなContractsプロジェクトに分離し、KioskにDB・OQS・Dynamics接続処理を持ち込まない。
- iCallの画面取得と操作は引き続きiCallManagerが担当する。Agentから既存ファイルAPIを呼ぶ。
- 職員コンソールと受付エンジンのコードを分ける。初期は同一プロセスでよいが、将来エンジンを別プロセスへ切り出せる形にする。初期構成ではAgent終了でKiosk受付が利用不可になる。

## 通信

ReceptionAgent側に小さなHTTP APIを設ける案を推奨。同一PCではlocalhost、専用MiniPCでは接続先URLを変更する。KioskとAgent間でSMB共有やXML・SQLiteへの直接アクセスは行わない。AgentとiCallManager間の既存ファイルAPIは維持する。

初期は約1秒間隔の状態取得で十分。実機で必要になってからイベント配信を検討する。LAN運用では端末の登録・認証と暗号化通信を用意し、患者用APIに職員用設定変更を公開しない。

| 操作 | API案 | 意味 |
|---|---|---|
| 接続確認 | GET /health | Agent・監視・必要な連携の利用可否 |
| 開始 | POST /sessions | 端末ID・コマンドIDを渡して受付セッション作成 |
| 入力 | POST /sessions/{id}/answers | 受診歴、氏名カナ、生年月日、既知の診察券番号など |
| 顔認証待ち開始 | POST /sessions/{id}/face-session | 照合入力を確認し、リーダー待機枠を確保 |
| 状態取得 | GET /sessions/{id} | 状態、バージョン、表示画面、メッセージ、許可されたボタン |
| 中止 | POST /sessions/{id}/cancel | 待機終了。送信済み外部操作は取り消した扱いにしない |
| 完了画面を閉じる | POST /sessions/{id}/acknowledge | 表示終了を記録し、Kioskを次の患者用に戻す |

変更要求には一意なcommandIdを付け、同一要求再送は同じ結果を返す。状態にはversionを付け、古い画面からの入力・ボタン操作は拒否する。別端末のセッションは取得・変更できないようにする。

## セッション

`KioskSession` は受付開始から完了・中止までの全体、`FaceSession` はXMLを1件結び付けるための一回限りの待機、と分ける。XML採用後にFaceSessionは消費するが、KioskSessionは結果表示まで継続する。

保持項目はsessionId、deviceId、状態、version、開始日時、有効期限、設定バージョン、患者入力、faceSessionId、採用captureId、分類・本人確認の状態、表示案内、職員対応状況、操作履歴。

初期の状態遷移:

```text
開始 → 入力 → FaceSession有効化 → カード操作案内 → XML待機
    → XML採用 → 患者・予約照会 → 分類結果
    → 案内表示／追加入力／職員確認 → 表示終了
```

XML待機の初期タイムアウトは60秒程度とし設定可能。XML採用後の照会待機は別タイムアウトにする。通信切断、XML待機時間切れ、照会時間切れ、職員確認、キャンセルは個別の状態・案内にする。再起動後は同じsessionIdの状態を照会し、無条件で別セッションを開始しない。

初期は同時に有効なFaceSessionをシステム全体で1つに制限する。リーダー識別情報が確認できた段階でリーダー単位の占有へ拡張する。ソフト上の占有は窓口でのカード操作を物理的に防げない。

## XMLとの対応付け

AgentがFaceSession有効化を返してからカード操作を案内する。開始時点で既に取得したXMLを採用しない。生成時刻・取得時刻、有効時間、事前入力の生年月日と氏名カナ、既知の診察券番号などを組み合わせて照合する。時刻や生年月日だけでは採用しない。

初期は職員が入力を補助する。同じ生年月日の別患者、姓名の表記揺れ、改姓、既知番号との矛盾、複数XML候補は追加確認または職員介入へ進める。一致しないXMLは通常のAgent処理を続け、Kioskへ割り当てない。

セッションとcaptureIdの対応をDBトランザクションで保存し、captureIdはセッション間で重複使用不可にする。確定後の再読取り・再生成XMLを次の患者へ勝手に割り当てない。キャンセル後や期限切れ後に届いたXMLを後続セッションへ時刻だけで引き継がない。

XML生成日時は秒精度・端末時計の影響がある。開始時の既存取込一覧と時刻比較を併用し、同じ秒の競合は別人と混同せず確認対象にする。将来の専用リーダー運用では、その出力元を識別できる実データの確認が重要。

## 分岐とメッセージ設定

案内設定はAgentで編集・保存・プレビューする。4分類ごとに、案内タイトル、本文、補足、表示するボタン、表示時間、次の画面を設定する。初期は固定の分岐選択肢を使い、自由記述の条件式・スクリプトを実行する仕組みは作らない。

| 基本分類 | 初期案内例 |
|---|---|
| カルテあり・予約あり | 予約を確認しました。職員の案内をお待ちください。 |
| カルテあり・予約なし | この一覧では予約を確認できませんでした。受付へお声掛けください。 |
| カルテなし・予約候補あり | お名前と生年月日が一致する予約候補があります。受付で確認します。 |
| カルテなし・予約候補なし | 診察券をお持ちの場合は番号をご入力ください。番号が不明な場合は受付へお声掛けください。 |

優先順位は「エラー・本人不一致・職員確認」→「必要な追加入力」→「4分類の通常案内」。照会中・未確認・要確認を4分類へ無理に変換しない。

現在のReceptionCategoryは受付時のカルテ取得有無による表示分類で、実際の受診歴ではない。Kioskには別途 hasVisitedBefore、patientIdentityStatus、reservationMatchStatus を保持する。「受診したことがある」かつカルテ未特定なら新患作成へ自動誘導せず、診察券番号・旧姓入力または職員確認へ進める。

find_candidatesの1件・氏名完全一致も本人確認が必要な予約候補。予約候補ありと患者・予約確定を区別し、初期は自動来院確認や連携へ直結させない。「受付完了」は案内表示の終了ではなく、必要な実操作の完了を確認できた場合に限る。現在のinvoked応答は操作送信であり、完了の証明ではない。

メッセージ差込みは受付番号等の許可した値だけにする。患者向け画面には内部ID、XML原文、保険証番号、COMエラーなどを出さない。設定はセッション開始時のバージョンに固定し、途中の編集で案内を変えない。将来の実操作の許可はメッセージ編集と別の設定にする。

## 職員コンソール

AgentにKioskセッション一覧を追加する。端末、現在画面、待機時間、対応XML、分類、患者・予約の確認状況、呼出し理由を表示する。職員は対応開始、患者確認、案内再表示、取消・終了を操作する。職員入力には担当・日時・変更理由を記録する。

現在のXML一覧は診療データ処理の履歴、Kioskセッション一覧は患者の操作進行を表す。両者はcaptureIdでリンクさせる。後からのWKO照合・照会番号訂正は職員コンソールへ反映し、既に終わったKioskや次の患者の画面へ古いセッションの通知を表示しない。

## 主な確認事項と初期実装範囲

1. 共有カードリーダーの誤紐付けが最大の問題。職員テストでは操作を順番に行い、DOB＋氏名カナ等の照合を必須にする。将来専用PCを置くだけでは解決しない。
2. 同一PCではタッチと職員入力のフォーカス競合がある。初期は職員操作の通常ウィンドウでテストし、業務との同時使用を前提にしない。
3. 予約なしの結果は現在のiCall一覧のみを対象とする。予約一覧・予約枠の種類や表示画面が違う場合は職員へ回す。
4. Agent停止・未監視・通信切断時はカード操作や受付完了を案内しない。Kioskを「職員へお声掛けください」にする。
5. 二重タップ・再送・再起動・離席・取消後のXML・同じ患者の再読取りを最初からテストする。
6. 表示終了・放置タイムアウトで入力・氏名等を画面から消す。テスト画面と患者運用画面を分け、患者画面から職員機能へ進めないようにする。
7. 時間計測は既存XML生成→分類確定に加え、セッション開始→XML採用、XML採用→分類確定、開始→案内表示を分ける。通信タイムアウトの判定はAgentを基準にする。

第一段階はKiosk画面、セッション開始・入力・取消・再接続、XML紐付け、4分類と例外案内、Agent側の案内設定・セッション一覧を実装する。サーバー側でテストモードを強制し、Kioskから来院確認・連携・新患作成・発券を自動実行しない。これらの実操作は、各完了条件を確認して次段階で接続する。

テストには架空XMLと架空の予約応答を使うシミュレーションモードを用意する。シミュレーションデータは実患者の取込・登録履歴と分け、画面とコンソールにテスト中であることを表示する。
