# ReceptionAgent 実装・確認手順

## 現在の構成

`ReceptionSystem.slnx` に iCallManager と ReceptionAgent を配置しています。
ReceptionAgent は独立した WinForms EXE、Core はUI/COMに依存しない登録処理です。

- メインフォーム：face XML検知 → 患者ID → 予約番号 → Dynamics受付転送 → iCall操作 → 発券の表示枠。受付処理そのものは未接続です。
- 別フォーム「照会番号 Bulk Console」：患者番号範囲、医療機関コード、OQSフォルダー、Dynamics項目対応、履歴、開始／再開／一時停止。
- 電光表示：現在の処理だけ500ms間隔で点滅。受付番号取得と最終登録成功を区別。
- 従来の手入力XML作成は「単件XMLの作成・確認」から開けます。こちらはローカルWork保存のみです。

## Dynamics接続

OQSDrug2 の `DynamicsComReader.cs` を参考に、起動済み Access.Application にSTAで接続します。Accessを新規起動したりMDBを開き直したりしません。接続先には「患者マスター」フォームが開いている必要があります。

フォームのRecordSourceを読み、同じAccessのCurrentDbからDAOの読取専用スナップショットを作ります。フォームのRecordSource、フィルター、選択患者は変更しません。借用したCurrentDbをCloseしたりAccessをQuitしたりしません。

ユーザー提供のSQLに基づき、次のテーブル／クエリを使用します。

| 用途 | 参照元 |
| --- | --- |
| カルテ番号 | 患者マスター.カルテ番号 |
| 保険との結合 | 患者保険マスター.カルテ番号 |
| 保険者・記号・番号 | 患者保険マスター.保険者番号／記号／番号 |
| 保険証枝番 | 患者保険マスター.枝番（固定） |

「Dynamics COM診断」は `WHERE 1=0` で項目名・型とフォームRecordSourceを表示します。患者データは読みません。取得結果を患者マスターとしてローカルに複製しません。

**確定した項目対応と残る確認事項**

1. 保険証枝番は患者保険マスター.枝番で確定。空欄を00に補完しません。
2. 照会番号はカルテ番号を10で整数除算した値で確定（例：244347 → 24434）。末尾7はDynamicsの枝番で、保険証の枝番とは別です。変換はDynamics側だけで実行し、画面では変更できません。
3. 複数の異なる健康保険が返る患者の選択ルール。現在は先頭の保険や「主保険」の未確認コードを推測して採用せず、AMBIGUOUS_INSURANCEとします。

現在の範囲指定は1～999999999の整数です。診察券番号の先頭ゼロに独立した意味がある運用は未対応です（手入力XML生成は先頭ゼロを保持します）。枝番なし患者IDに対応する内部カルテ枝番0～9を検索し、異なる保険が複数あれば要確認とします。

## 初回の使い方

1. Dynamicsで患者マスターフォームを開く。
2. ReceptionAgentの「照会番号 Bulk Console」→「Dynamics COM診断」で項目対応を確認。
3. メイン画面の「設定」で既存req/resを含むOQS連携フォルダーを保存。医療機関コードは範囲保存時にDynamicsから自動取得します。Bulk画面の枝番フィールドと変換チェックボックスは削除済みです。
4. まず診察券番号1名だけを開始・終了に指定し「範囲を保存」。設定はその範囲の履歴に保存されます。
5. 「開始／再開」で実際のreqへ要求が送信されます。フォルダー設定を変更した場合、新しい範囲または未着手の範囲を保存し直してください。処理履歴がある範囲は保存済みの送信先を使用します。
6. 成功は02resの患者別結果で確認します。01resの受付番号だけでは成功になりません。
7. 実機での受理と次回来院時のface XMLのReferenceNumberを確認してから範囲を広げます。

医療機関コードや患者情報の実値は初期値に含めていません。ここまでの自動テストでは架空データのみを使用し、実サーバーに送信していません。

## 登録処理と履歴

初期版は1患者ずつ順番に処理します（複数患者を1ファイルにまとめる方式ではありません）。

`保険取得 → 01req → 01resの受付番号 → 02req → 02resの患者別結果`

- 要求はShift_JIS、日付＋4桁連番、任意ファイル識別子付き。
- 保険者番号は8桁に満たなければ左を空白で埋めます。ゼロ埋めはしません。
- reqは一時ファイルを書いてflush後にリネーム。既存ファイルは上書きしません。
- 応答は要求に対応するファイル名だけを読み、医療機関・任意識別子・受付番号・患者／保険のフィンガープリントを照合します。
- XMLは共有読み取りし、2回同じ内容になるまで待機します。DTD/外部実体は禁止です。
- 成功、失敗、患者なしを別集計。「最終処理番号」と「最終成功番号」を分けます。途中の失敗を登録済みとは扱いません。
- 送信意図を先に永続化します。停止、タイムアウト、送信の成否が不明な場合は自動で同じ登録要求を再送しません。
- 再開は保存した要求の応答待ちから行います。応答がなければ保留します。管理者が元のreq/resを確認してください。
- 同じ医療機関の重なる範囲を新規作成することは防止します。送信前かつ処理履歴が空なら選択範囲の設定を更新できます。
- 1日4桁連番は01/02で共用するため、両方を当日発行する通常処理では最大4999患者程度です。単件XML保存でも連番を消費します。

保存先:

```text
%LOCALAPPDATA%/ReceptionAgent/
  reference_request_sequence.txt
  ReferenceRegistration/Jobs/<job-id>.json
  ReferenceRegistration/Jobs/bulk.lock
  Work/ReferenceNumber/   # 手入力XMLで明示的に保存したもの
```

JSONには範囲・設定・患者ID・要求名・受付番号・状態・結果コード・日時・照合用ハッシュを保存します。氏名・住所・保険証番号全文は保存しません。サーバー自由文メッセージにも患者情報が入る可能性があるため、その全文は元のres XMLで確認します。req/resは削除・移動しません。履歴保存先はWindowsユーザーごとなので、同一OQSへの実行端末／ユーザーは1つに固定してください。

## 残っている実機確認・未対応範囲

- Dynamics実機でのCOM読み取り検証と、複数保険の選択ルールの確認。枝番フィールドと内部カルテ番号変換は確定済み。
- 現行OQS実応答の形式・受付/処理中コードの確認。現在は提供仕様のXML構造を厳密に照合します。
- 未知の応答や結果未確定の応答を受けたときの自動ダウンロード再要求。現在は成功にせず保留します。
- ZIP応答、公費XML、枝番が省略可能な保険の条件分岐。
- 失敗患者だけの新規再試行と、送信成否不明時の手動復旧UI。現在の「再開」は結果待ちの再開であり、失敗済み患者の再登録ではありません。
- face XMLの監視、患者照合、iCall通信、Dynamics受付転送、発券。

## 古い保険情報での登録

登録済み照会番号が同一人の保険者変更後も引き継がれることは、[オンライン資格確認操作マニュアル](https://iryohokenjyoho.service-now.com/csm/sys_attachment.do?sys_id=f416a214c3e6ea549607f81a0501315f)に記載があります。

ただし、任意の古い保険情報からの初回登録が必ず受理されるとは確認できていません。初回登録の成否は実応答で記録し、資格の有効性とは別に扱います。古い受診日だけを理由に対象外にはしていません。保険情報欠落、枝番不明、候補複数は要確認とし、最新情報を確認できた段階で再登録する運用を想定します。

参考：[厚生労働省 技術解説書（令和7年12月）](https://www.mhlw.go.jp/content/10200000/000575785.pdf)。照会番号登録の構造はユーザー提供仕様および公開の旧XMLレイアウトを参考にしています。現行実サーバーでの受理は未検証です。

## 医療機関コードの自動取得とアプリ設定

医院情報の県番（2桁）＋点数表（1桁）＋医療機関コード（7桁）を連結してOQS用の10桁にします。数値型で失われた先頭ゼロは各項目の指定桁数に補完します。項目の欠落、非数字、桁超過、医院情報が0件または複数件の場合は取得失敗とし、手入力値にフォールバックしません。

範囲保存時と患者取得時に起動中のDynamicsから読み取ります。保存範囲と接続先の医療機関コードが異なれば、新しい患者の登録を停止します。送信済み要求の結果確認は保存済みコード・送信先を使うため、Accessが閉じていても再開できます。単件XML確認画面でも医療機関コードは自動取得・読み取り専用です。

メインフォームの「設定」からOQS親フォルダーを指定します。設定保存先は `%LOCALAPPDATA%\ReceptionAgent\settings.json`。絶対パス・UNC・環境変数を使用できます。設定時は接続先を作成せず、実行時にreq/resの存在を確認します。設定破損時は黙って初期化しません。

Bulkフォームの診察券番号指定、保存／開始／一時停止、履歴、進捗、結果一覧は維持しています。上部は保存範囲の医療機関コード・OQSフォルダーの参照表示のみです。
